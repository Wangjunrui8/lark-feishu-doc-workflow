# AI 智能周报

从多个飞书数据源自动采集本周工作信息，生成结构化周报，通过飞书私信交付（bot 发送 Markdown 全文）。

## 工作流概览

1. 确定周报周期（默认本周一~周日）
2. 采集数据（信息共享表 + 信息收集表 → 任务 → 消息 → 本周文档 → 个人日报）
3. 按业务子域分组整理（两张表记录合并去重后统一分组；子域名只标注一次作为标题，条目汇总其下）
4. **生成前校准检查**（任务不能丢 / 文档有的要沉淀 / 样式不能丢）
5. 生成周报（本周概览 → 本周工作 → 下周计划 → 需要协调和帮助 → 风险与策略 → 建议）
6. 通过飞书私信交付周报全文

## Step 1: 确定周报周期

- 默认：本周一 00:00 ~ 本周日 23:59（基于系统注入的周历表推算）
- 用户指定其他周期时，按用户指定的日期范围执行

## Step 2: 采集数据

按优先级依次从 5 个数据源采集，每个数据源独立调用、互不依赖，可并行执行。

详细的数据源映射、API 调用方式和提取逻辑见 [data-sources.md](references/data-sources.md)。

### 2.1 大前端项目信息共享表（核心数据源）

```bash
# 获取字段结构（首次执行时确认字段名）
lark-cli base +field-list \
  --base-token HZpJbvuLPaEFBXskUi1cyouonLh \
  --table-id tbl6a70HjOPmq5AS \
  --as user

# 拉取记录（使用默认视图）
lark-cli base +record-list \
  --base-token HZpJbvuLPaEFBXskUi1cyouonLh \
  --table-id tbl6a70HjOPmq5AS \
  --view-id vewu9HlQU8 \
  --as user \
  --format json
```

从结果中按以下两层规则筛选当前登录用户的记录，按**业务子域**分组：

**第一层 — 需求 Owner（按状态过滤）**：
- 「需求 Owner」为当前登录用户的记录，纳入以下状态：需求沟通、待排期、已排期、开发中、测试中、待发布、暂停、废弃、临时
- **已发布**状态：仅保留「上线时间」落在**本周**范围内的记录，非本周上线的不纳入周报

**第二层 — 任务执行人（按状态过滤）**：
- 「任务执行人」为当前登录用户的记录，仅保留以下状态：
  - **待排期** — 尚未启动，用于下周计划参考
  - **开发中** — 正在开发，标注进度百分比
  - **测试中** — 进入测试阶段，标注进度百分比
  - **待发布** — 测试通过，等待发布上线
  - **暂停** — 已暂停，标注暂停原因（如有）
  - **废弃** — 已废弃，标注废弃原因（如有）
  - **临时** — 临时性需求
  - **已发布** — 仅保留「上线时间」落在**本周**范围内的记录

不满足以上任一条件的记录一律丢弃。

### 2.2 飞书任务

```bash
# 未完成的任务
lark-cli task +get-my-tasks --complete=false --format json

# 已完成的任务
lark-cli task +get-my-tasks --complete=true --format json
```

按 `completed_at` / `updated_at` 过滤本周范围。

### 2.3 飞书消息

```bash
# @我的消息
lark-cli im +messages-search \
  --is-at-me \
  --start "YYYY-MM-DDT00:00:00+08:00" \
  --end "YYYY-MM-DDT23:59:59+08:00" \
  --as user \
  --format json

# 关键词搜索（可多次调用，关键词如项目名、"评审"、"上线"等）
lark-cli im +messages-search \
  --query "关键词" \
  --start "YYYY-MM-DDT00:00:00+08:00" \
  --end "YYYY-MM-DDT23:59:59+08:00" \
  --as user \
  --format json
```

提炼关键讨论结论和决策，不要逐条罗列消息。

### 2.4 本周创建的文档

```bash
# 搜索本周我创建的云文档（--created-by-me 限定我创建，created-since/until 限定时间窗）
lark-cli drive +search \
  --query "" \
  --doc-types docx \
  --created-by-me \
  --created-since "YYYY-MM-DDT00:00:00+08:00" \
  --created-until "YYYY-MM-DDT23:59:59+08:00" \
  --as user \
  --format json
```

> 注意：旗标是 `--doc-types`（非 --docs-types）、`--created-since/--created-until`（非 --start-time/--end-time），写错会报 unknown flag。

对搜索到的每篇文档，执行以下处理流程：

**Step 1 — 读取内容并过滤空文档**：
- 使用 `lark-cli docs +fetch --doc-id <token>` 读取文档正文
- **内容不能为空**：跳过纯模板、空白页或无实质内容的文档，只保留有实质内容的文档

**Step 2 — 关联到具体任务**：
- 将每篇文档的标题和关键内容与 Step 2.1 中采集的多维表格记录（需求名称、业务子域）进行匹配
- **能关联到已有任务的文档**：归入对应业务子域的「本周工作」章节，作为该任务的补充说明（如技术方案、设计文档等）
- **无法关联到已有任务的文档**：归入「本周工作」下的**「文档沉淀」**分组，作为独立产出展示

**Step 3 — 提取价值要素**：
- 对有实质内容的文档，提取以下关键要素：
  - 文档标题和主题
  - 核心结论、决策、方案要点
  - 重要的技术设计或架构变更
  - 创新性思路或方法论沉淀
- 这些价值要素同时沉淀到**「四、建议」**章节，作为分析的数据支撑

### 2.5 大前端项目信息收集表

```bash
# 获取字段结构（首次执行时必须确认字段名）
lark-cli base +field-list \
  --base-token QW4Yb41d6aG28msz7fNc356hn6e \
  --table-id tblf7W8KfVj1fZkZ \
  --as user

# 拉取记录（使用默认视图）
lark-cli base +record-list \
  --base-token QW4Yb41d6aG28msz7fNc356hn6e \
  --table-id tblf7W8KfVj1fZkZ \
  --view-id vewK87mK8K \
  --as user \
  --format json
```

筛选规则（单层）：
- 仅保留「需求 Owner」为当前登录用户的记录，**不论需求状态，全部纳入周报**
- **例外**：状态为「已发布」的记录，仅保留「上线时间」落在本周范围内的记录，非本周上线的不纳入周报
- 不满足此条件的记录一律丢弃

**合并去重**：将 2.1 和 2.5 两张表的筛选结果以「需求名称」为键合并去重，同名需求优先保留信息共享表的记录（字段更完整），仅出现在收集表中的需求正常纳入。

### 2.6 个人日报

```bash
lark-cli docs +fetch --doc RCu2dMKtioZKuDxQNuscCd3VnIB --doc-format markdown --as user
```

- 日报文档按月份组织（一级标题「X月日报」），每天一个二级标题（如 `## **2026 - 8 - 12**`，日期数字间有空格、无前导零），每天含「今日工作内容 / 遇到的问题与阻塞 / 明日工作计划」三段
- 仅提取日期落在本周范围内的每日小节；作为「本周工作」的逐日事实底稿，与其他数据源交叉印证、补充未进多维表格的零散工作（评审、联调、培训等）
- 「遇到的问题与阻塞」中的未解决项流入「需要协调和帮助」/「风险与策略」章节；最后一天的「明日工作计划」作为「下周计划」的参考输入
- 若日报文档读取失败或缺少本周条目，标注「日报数据未获取/未填写」，不编造

## Step 3: 分组整理

将所有采集到的数据按以下维度归类：

| 周报章节 | 数据归类规则 |
|----------|-------------|
| 本周工作 | 信息共享表 + 信息收集表合并去重后的需求进展、已完成任务、关键沟通决策；能关联到具体需求的文档作为对应需求子条目；无法关联的文档归入「文档沉淀」分组 |
| 下周计划 | 进行中和待处理的需求/任务、下周已安排的日程 |
| 需要协调和帮助 | 状态为阻塞/延期的需求、讨论中提到的卡点和依赖 |
| 风险与策略 | 进度滞后的需求（开发中但进度低于预期）、依赖外部方的待发布需求、技术方案尚未确定的开发中需求、资源冲突或排期冲突；针对每个风险给出应对策略 |
| 建议 | 基于本周文档产出（逐篇读取提取价值要素）和日常沟通，挖掘能力提升建议及解决问题带来的价值 |

**分组原则**：
- **业务子域只标注一次**：以子域名为标题（如 `### 用户增长`），其下汇总该子域所有相关条目，不重复标注子域
- 本周工作和下周计划均按业务子域分组
- 按任务等级排序（P0 > P1 > P2 > P3）
- 每条记录简明扼要，包含关键状态和进度信息
- 无明确子域的条目归入「其他」分组

## Step 3.5: 生成前校准检查（必执行）

在进入文档生成之前，**必须**逐条完成以下三项校准。任一校准未通过，不得进入 Step 4。

### 校准一：任务不能丢

确保从各数据源采集到的任务条目**全部**进入周报，无一遗漏。

**校准方法**：

1. **计数对账**：统计 Step 2 采集到的各数据源条目数，与 Step 3 分组整理后的条目数逐一比对：
   - 信息共享表筛选后的记录数 → 本周工作中应有对应条目数
   - 信息收集表筛选后的记录数（去重后新增的） → 本周工作中应有对应条目数
   - 飞书任务（本周已完成） → 本周工作中应有对应条目数
   - 飞书任务（未完成，截止日期在下周） → 下周计划中应有对应条目数
   - 飞书消息提炼的决策项 → 本周工作或协调帮助中应有对应条目数

2. **交叉比对**：将采集阶段每一条原始记录与分组结果做一次 name/id 级别比对。若某条记录在分组结果中找不到对应条目，必须查明原因（是被合理过滤还是意外遗漏），合理过滤的标注说明，意外遗漏的补回。

3. **遗漏补救**：发现遗漏时，将遗漏条目补入对应章节和业务子域分组；无法确定归属的，归入「其他」分组并标注来源。

### 校准二：文档有的要沉淀

确保本周创建的每一篇有实质内容的文档**全部**出现在周报中，不得被静默丢弃。

**校准方法**：

1. **全量盘点**：列出 Step 2.4 搜索到的所有文档（含被 Step 1 过滤掉的空文档），逐一标注去向：
   - 空文档/无实质内容 → 标注「已过滤（空文档）」，不纳入但留痕
   - 能关联到具体任务的 → 标注「已归入 [业务子域] / [需求名称]」
   - 无法关联的 → 标注「已归入文档沉淀分组」

2. **计数核验**：文档总数 = 已过滤数 + 已关联数 + 文档沉淀数。三者之和必须等于搜索到的文档总数，任何对不上的情况都要回查。

3. **价值要素核验**：确认每篇有实质内容的文档的价值要素（标题、核心结论、技术要点）都已提取并沉淀到「四、建议」章节作为素材。

### 校准三：样式不能丢

确保周报的 Markdown 结构与优先级/状态标注**完整、正确**，与模板规范一致。

**校准方法**：

1. **标注完整性**：逐条检查每个条目：
   - P0 优先级是否标注为（🔴 **P0**）
   - 状态是否按标注规则表标注了对应记号（已发布→✅、开发中/待发布→🟠、测试中/联调中→🔵、阻塞/延期/暂停→🔴、待排期/废弃/临时→纯文字）
   - 不得出现「有状态文字但无标注」或「标注与状态不匹配」的情况

2. **Markdown 结构完整性**：
   - 层级正确：`#` 周报标题 → 📋 本周概览总结段 → `##` 五大章节 → `###` 业务子域
   - 本周概览紧跟标题之后，内容为一段话（2-3 句），不使用列表
   - 每个业务子域下使用 `-` 列表结构
   - 文档沉淀分组放在本周工作末尾，有独立 `###` 标题
   - 六个章节（本周概览 / 本周工作 / 下周计划 / 需要协调和帮助 / 风险与策略 / 建议）齐全，缺一不可

3. **内容格式规范**：
   - 每条需求包含：需求名称（加粗）+ 优先级 + 状态（带标注）+ 进度/说明
   - 「需要协调和帮助」无阻塞项时写「本周无需要协调事项」
   - 「建议」章节基于真实文档和沟通记录，不空泛

### 校准结果

三项校准全部通过后，方可进入 Step 4 生成周报。校准过程中发现的问题及修复情况，在最终交付时简要说明（如「校准检查：补回 2 条遗漏任务，确认 3 篇文档全部沉淀」）。

## Step 4: 生成周报

周报模板和各章节生成规则见 [report-template.md](references/report-template.md)。

### 本周概览（周报第一个章节）

本周概览是周报的开篇总结，提供本周工作的高层快照。**保持精简，2-3 句话概括即可，不做罗列**。

**内容要求**：
- 一段连续文字，不使用列表
- 第一句：需求总数 + 关键状态分布（上线发布列出具体名称，其余状态只说数量）
- 第二句：其他重要完成事项（从飞书任务、消息、文档中提炼非需求跟踪表内的事项，用顿号或逗号串联，不逐条展开）

**Markdown 结构**：
```markdown
📋 **本周概览：**共跟踪 24 项需求，其中 3 项本周上线发布（能源盒子邀约下发、南向通用化改造迭代一、赛意-渠道客户系统），7 项进入测试阶段，6 项持续开发中，5 项待排期。完成 vpp 项目主干合入与基线发布，参与基准价改造方案评审，推进线损与日清算设计验收问题整改。完成 Q3 OKR 制定，发布 AI 智能周报到 Aily 技能市场并编写配套文档。
```

> 数据来源：需求统计来自 Step 2.1 + 2.5 合并去重后的记录；其他完成事项从飞书任务、消息、文档中提炼，排除已归入多维表格记录的事项。

### 优先级与状态标注规则（重要）

在周报中为每条需求的**状态**和**优先级**添加标注，使周报一目了然：

**优先级标注**：
- **P0**：必须用红圈加粗标注 → `(🔴 **P0**)`
- P1/P2/P3：正常文字显示即可 → `(P1)` / `(P2)` / `(P3)`

**需求状态标注**（状态文字前加对应记号）：
- **已发布上线 / 已完成** → `✅ 已发布上线`
- **测试中** → `🔵 测试中`
- **开发中** → `🟠 开发中`
- **待发布** → `🟠 待发布`
- **待处理 / 待启动 / 待排期** → 纯文字 `待排期`
- **暂停** → `🔴 暂停`
- **废弃** → 纯文字 `废弃`
- **临时** → 纯文字 `临时`
- **阻塞 / 延期** → `🔴 阻塞`
- **联调中** → `🔵 联调中`

**示例**（完整的条目）：
```markdown
- **能源盒子邀约下发**（🔴 **P0**）：✅ 已发布上线，新增户号列表功能
- **电价统一管理-市场化结算均价**（🔴 **P0**）：🟠 开发中，进度 80%，等待后端接口联调
- **南向迭代二**（🔴 **P0**）：🔵 测试中，进度 85%
- **驾驶舱-虚拟电厂**（P1）：🟠 开发中，进度 90%
```

### 周报内容结构参考（Markdown）

```markdown
# YYYY年MM月DD日 - MM月DD日 工作周报

📋 **本周概览：**共跟踪 24 项需求，其中 3 项本周上线发布（能源盒子邀约下发、南向通用化改造迭代一、赛意-渠道客户系统），7 项进入测试阶段，6 项持续开发中，5 项待排期。完成 vpp 项目主干合入与基线发布，参与基准价改造方案评审，推进线损与日清算设计验收问题整改。完成 Q3 OKR 制定，发布 AI 智能周报到 Aily 技能市场并编写配套文档。

### 文档沉淀
以下为本周创建的文档，未能关联到具体需求，作为独立产出记录：
- **文档标题**：核心要点摘要

（注：能关联到具体需求的文档，已归入对应业务子域的条目中）

## 二、下周计划

### 业务子域A

## 三、需要协调和帮助
```
